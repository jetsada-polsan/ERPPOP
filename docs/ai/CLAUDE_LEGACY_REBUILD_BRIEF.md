# งานสำหรับ Claude: ตรวจความพร้อม POPSTAR ERP/POS และถอดรายงานจากระบบเดิม

## เป้าหมายของโครงการ

POPSTAR กำลังสร้าง ERP และ POS ของตนเอง โดยศึกษา flow และคู่มือของ BPlus เดิมเป็นต้นแบบทางธุรกิจเท่านั้น ระบบใหม่ **ไม่ใช่การคัดลอก BPlus** และไม่ต้องผูกกับโครงสร้างฐานข้อมูลเดิม

ระบบเป้าหมายคือ:

- Web ERP: PHP, Laravel, PostgreSQL
- POS Desktop: Vue 3, TypeScript, Tauri, SQLite ในเครื่อง Windows
- POS sync กับ ERP ผ่าน API ภายใต้ `/api/pos/*`
- ระบบใหม่ต้องออกแบบให้ใช้งานง่ายกว่า ตรวจสอบย้อนหลังได้ และคุมสิทธิ์/ราคา/สต๊อก/บัญชีได้ชัดเจน

## เอกสารและข้อมูลที่จะได้รับ

เจ้าของจะส่งให้เพิ่มภายหลัง:

1. คู่มือใช้งาน BPlus เดิม (PDF/CHM)
2. ไฟล์ SQL เก่า, schema, query หรือ export report
3. ภาพตัวอย่างหน้าจอและรายงานที่ใช้จริง

ให้ใช้ข้อมูลเหล่านี้เพื่อเข้าใจความหมายทางธุรกิจ, รายงาน, เอกสาร และการคำนวณเท่านั้น

## ข้อห้ามเด็ดขาด

- Legacy MSSQL (`192.168.88.200`) เป็น **read-only**.
- ใช้ได้เฉพาะ `SELECT`; ห้าม `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `ALTER`, `DROP`, `CREATE`, stored procedure, job หรือคำสั่งเขียนใด ๆ.
- ห้ามนำ credentials, token, password หรือข้อมูลลูกค้าส่วนบุคคลไป commit.
- ห้ามสร้างตาราง/โมดูลใหม่เพียงเพราะ BPlus มี ต้องพิสูจน์ก่อนว่าบริษัทใช้จริงและมี owner ของข้อมูล.
- ห้ามนำเข้าประวัติ POS เดิมเข้าระบบใหม่ เพราะเลขเอกสาร, สาขา, terminal และชื่อสาขาเปลี่ยนแล้ว; legacy ใช้เพื่ออ้างอิงและกระทบยอดเท่านั้น.

## งานระยะที่ 1: Audit ความพร้อมระบบใหม่

อ่านก่อน:

```bash
git checkout main
git pull origin main
cat docs/ai/PROJECT_MEMORY.md
cat docs/pos-flow-redesign.md
cat docs/architecture/LEGACY_TABLE_SCOPE_POLICY.md
cat docs/architecture/BPLUS_ERP_REBUILD_BLUEPRINT.md
```

จากนั้นตรวจระบบใหม่จริงและทำรายงาน `docs/ai/erp-readiness-audit.md` โดยจัดลำดับเป็น:

### A. พร้อมใช้งานแล้ว

ระบุโมดูล, flow ที่รองรับ, ไฟล์/route/model ที่ยืนยัน และ test ที่รันจริง

### B. มีแล้วแต่ยังไม่พร้อมใช้งานจริง

ระบุช่องว่าง เช่น validation, approval, audit trail, permission, UAT, report, migration, POS hardware หรือ error recovery

### C. ยังไม่มีและต้องเพิ่ม

จัดลำดับ P0/P1/P2 พร้อมเหตุผลธุรกิจ, owner, ข้อมูลเข้า, เอกสารผลลัพธ์, ผลต่อ stock/GL/AR/AP และ test ที่ต้องมี

ตรวจทุกกลุ่มนี้:

1. แฟ้มหลัก: สินค้า, หน่วย, บาร์โค้ด, หมวด, ราคา, ลูกค้า/ลูกหนี้, ผู้ขาย, สาขา, คลัง, พนักงาน/สายขาย
2. ซื้อ/รับเข้า: PR, PO, รับสินค้า, ต้นทุน, คืนผู้ขาย
3. สต๊อก: ย้าย, ปรับ, ตรวจนับ, lot/หมดอายุ, สูญเสีย, แปรรูป/จัดชุด
4. ขายหลังบ้าน: ใบเสนอราคา, ใบจอง, ขายสด, ขายเชื่อ, ส่งของ, คืน/ลดหนี้
5. POS: token, catalog sync, offline queue, cashier, shift, promotion, price schedule, backup/restore, update, hardware/UAT
6. การเงิน/บัญชี: รับชำระ, bank/statement reconciliation, ค่าใช้จ่าย, AR/AP, GL posting, VAT/WHT, ส่งสำนักงานบัญชี
7. รายงานและ dashboard: ยอดขาย, GP/COGS, สต๊อก, คงค้าง, ลูกหนี้, เงินสด, ค่าใช้จ่าย, ผู้บริหาร
8. ความปลอดภัย/ปฏิบัติการ: สิทธิ์, audit log, backup, restore, monitoring, deploy, recovery

## กติกา flow ที่ห้ามเปลี่ยนโดยไม่มีเหตุผลและ UAT

| เอกสาร | สต๊อก | รายได้/ลูกหนี้ |
| --- | --- | --- |
| ใบเสนอราคา | ไม่ตัด ไม่จอง | ไม่บันทึก |
| ใบจอง | จองเพื่อติดตาม | ไม่บันทึก |
| ขายสดหลังบ้าน | ตัดเมื่อยืนยัน | รายได้เงินสด/โอน |
| ขายเชื่อ | ตัดเมื่อยืนยัน | เปิดลูกหนี้ |
| POS receipt | ตัดเมื่อขายเสร็จ | รายได้ POS |
| ส่งสินค้า | ห้ามตัด/รายได้ซ้ำ | ติดตามการส่ง |
| คืน/ลดหนี้ | รับกลับเมื่ออนุมัติ | ย้อนรายการต้นทางครั้งเดียว |

รายงานรวมต้องอ่าน `sales_postings` เพื่อไม่รวม POS กับเอกสารหลังบ้านซ้ำ

## งานระยะที่ 2: ถอดรายงานจาก SQL/รายงานเดิม

เมื่อได้รับไฟล์ SQL หรือ report export แล้ว:

1. ห้ามรัน SQL ที่ยังไม่ได้ตรวจว่า read-only.
2. ทำ inventory ที่ `docs/ai/legacy-report-catalog.md` ด้วยคอลัมน์:
   - ชื่อรายงานเดิม
   - ผู้ใช้/ฝ่ายที่ใช้
   - วัตถุประสงค์การตัดสินใจ
   - filter/parameter
   - ตาราง legacy ที่อ้างอิง
   - สูตรยอด/ต้นทุน/กำไร/ภาษี
   - ความถี่และช่วงเวลา
   - รูปแบบผลลัพธ์ (หน้าจอ, Excel, PDF)
   - รายงานใหม่ที่เทียบเท่าใน ERP
   - สถานะ: ready / needs mapping / excluded
3. เปรียบความหมายคอลัมน์กับ PostgreSQL ใหม่ อย่า map ตามชื่อที่คล้ายกันอย่างเดียว.
4. สร้าง query/report ใหม่เฉพาะเมื่อ mapping มี primary key, วันที่, สถานะเอกสาร, หน่วย และกฎยอดครบ.
5. ทุก report ต้องมี UAT เทียบตัวอย่างยอด legacy โดยอธิบายผลต่างเป็นจำนวนเอกสารและจำนวนเงิน.

## แนวทางรายงานใหม่

- ใช้ข้อมูลจาก PostgreSQL ระบบใหม่เป็นหลัก
- Legacy report ใช้เป็นแม่แบบ/ตัวเทียบยอด ไม่ใช่ dependency ถาวร
- รายงานยอดขายต้องแยก POS, ขายสดหลังบ้าน, ขายเชื่อ, คืน/ลดหนี้ และรวมแบบไม่ซ้ำ
- รายงานกำไรต้องระบุชัดว่าใช้ต้นทุนใด: actual issue cost, moving average, standard cost หรือ period average
- ทุก report ต้องเลือกช่วงวันที่, สาขา, คลัง, สายขาย และ export Excel/PDF ได้เมื่อเหมาะสม

## การส่งมอบงานแต่ละรอบ

ก่อนแก้โค้ด:

```bash
php artisan test
php artisan erp:health
```

หลังทำงาน:

1. รัน test ที่เกี่ยวข้องจริง
2. commit แบบแยกเรื่อง
3. push `main`
4. อัปเดต `docs/ai/task.md` ด้วย commit, สิ่งที่ทำ, test, ความเสี่ยง และงานถัดไป
5. ห้าม deploy จนกว่าเจ้าของอนุญาต

## นิยามความสำเร็จ

ไม่ใช่แค่มีเมนูครบ แต่ต้องพิสูจน์ว่าเอกสารหนึ่งใบไหลจากต้นทางถึง stock, revenue, debtor/cash, cost, GL และรายงานได้หนึ่งครั้งอย่างถูกต้อง พร้อมสิทธิ์, audit trail และ recovery ที่ใช้งานจริงได้.
