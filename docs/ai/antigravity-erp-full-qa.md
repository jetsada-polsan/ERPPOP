## สรุปภาพรวมการตรวจ (Overview)
งานนี้เป็นการตรวจสอบระบบ JET ERP (Laravel 13 + Blade + Alpine บน PostgreSQL/SQLite) ทุกโมดูล ทุกฟีเจอร์ ทุกปุ่ม เพื่อให้มั่นใจว่า:
1. ไม่มีหน้าใดเกิดข้อผิดพลาด Server Error (HTTP 500)
2. ผู้ใช้แต่ละบทบาท (GM, SALES, WAREHOUSE) ได้รับสิทธิ์ตรงตามบทบาท (หน้าที่ไม่มีสิทธิ์ต้องตอบกลับด้วย HTTP 403 Forbidden ไม่ใช่ 500)
3. ตรวจสอบการทำงานของปุ่ม ลิงก์ ฟอร์ม ตัวกรอง และกรณีขอบเขต (Edge cases) ทั้งหมด
4. รวบรวมรายการฟีเจอร์ที่ยังขาด และรายการที่ต้องส่งต่อให้ Claude ปรับปรุงเชิงลึกด้านบัญชี/การเงิน/สต็อก

## รอบที่ 2: ตรวจสอบทุกปุ่ม ฟอร์ม ตัวกรอง และกรณีขอบเขต (Manual QA & Edge-Case Automation)

### 2.1 สรุปการตรวจเช็กและแก้ไขข้อผิดพลาดในระดับ Query (SQLite Compatibility Fix)
ในการทดสอบค้นหาข้อมูลและกรองข้อมูลผ่านพารามิเตอร์ `?q=` หรือตัวกรองข้อความในหน้าตารางต่างๆ พบว่ามีกว่า 25 คอนโทรลเลอร์ที่ใช้คำสั่ง `where('...', 'ilike', ...)` ซึ่งเป็นคำสั่งมาตรฐานของ PostgreSQL (Case-insensitive) แต่เมื่อรันบน SQLite ในสภาพแวดล้อมทดสอบในเครื่อง จะทำให้เกิดข้อผิดพลาด:
`SQLSTATE[HY000]: General error: 1 near "ilike": syntax error`

**การแก้ไขที่ปลอดภัย:**
เพิ่ม Query Grammar Resolver สำหรับการเชื่อมต่อ SQLite ใน `app/Providers/AppServiceProvider.php` โดยแปลงโอเปอเรเตอร์ `ilike` เป็น `like` อัตโนมัติเฉพาะบน SQLite เท่านั้น โดยไม่มีการแก้ไขโค้ด Controller หรือกระทบพฤติกรรมบน Production (PostgreSQL) ทำให้การทดสอบค้นหาบนระบบจำลองทำงานได้อย่างสมบูรณ์

### 3.2 รายการ "ส่งต่อ Claude" (Handover to Claude: Deep Financial/Stock/Accounting Logic)
ตามกฎข้อห้ามอย่างเคร่งครัดที่ไม่อนุญาตให้แก้ไข Business Logic เชิงลึกด้านการเงิน สต็อก ภาษี และผังบัญชี ได้รวบรวมประเด็นขอบเขต (Edge Cases) และข้อเสนอแนะเชิงโครงสร้าง เพื่อให้ Claude พิจารณาปรับปรุงต่อไป:

#### 1. การกำหนด Tolerance Threshold สำหรับ Catch Weight ใน `CreditSaleService`
- **ไฟล์ที่เกี่ยวข้อง:** `app/Services/Sales/CreditSaleService.php`, `app/Services/Sales/BookingService.php`
- **เงื่อนไข/ปัญหา:** เมื่อแปลงใบจอง (Booking) เป็นใบขายเชื่อ (Credit Sale) พร้อมระบุน้ำหนักชั่งจริง หากผู้ใช้ป้อนน้ำหนักผิดพลาดรุนแรง เช่น สั่ง 10 กก. แต่คีย์ 100 กก. หรือค่าติดลบ ระบบจะคำนวณยอดเงินและตั้งหนี้ตามตัวเลขนั้นทันที
- **วิธีทำซ้ำ (Reproduction Steps):**
  1. เข้าเมนูแปลงใบจองเป็นใบขายเชื่อ
  2. แก้ไขจำนวน/น้ำหนักสินค้าในฟอร์มเป็น `100.00` (จากเดิมที่จองไว้ `10.00`)
  3. บันทึกข้อมูล ระบบจะสร้าง Credit Sale ด้วยยอดเงินเกินจริง 1,000% โดยไม่มีการแจ้งเตือน
- **ข้อเสนอแนะให้ Claude:** เพิ่มพารามิเตอร์ตรวจสอบ Variance Tolerance (เช่น อนุญาตต่างได้ไม่เกิน ±10% หรือ ±15% ของยอดจอง) หากเกินกำหนดให้ระบบแจ้งเตือนยืนยัน หรือต้องใช้สิทธิ์ Supervisor อนุมัติ

#### 2. การจัดการเศษสตางค์และการปัดเศษใน `CustomerPaymentService` (Allocation Rounding Difference)
- **ไฟล์ที่เกี่ยวข้อง:** `app/Services/Accounting/CustomerPaymentService.php`, `app/Support/DecimalMath.php`
- **เงื่อนไข/ปัญหา:** เมื่อลูกค้ารับชำระหนี้หลายบิลพร้อมกัน หรือมีการหักภาษี ณ ที่จ่าย (WHT 1% หรือ 3%) บ่อยครั้งเกิดเศษสตางค์คลาดเคลื่อน (เช่น ลูกค้าโอนเงินยอดถ้วน ขาดไป 0.25 บาท) ทำให้มี Open Item ยอดเศษสตางค์ค้างอยู่ในระบบตลอดไป
- **วิธีทำซ้ำ (Reproduction Steps):**
  1. สร้างใบขายเชื่อยอด 1,000.55 บาท
  2. ลูกค้าชำระเงินโอนยอดถ้วน 1,000.00 บาท
  3. ระบบจะบันทึกสถานะ Open Item ค้างชำระ 0.55 บาท ซึ่งต้องออกใบลดหนี้ (CN) เพื่อล้างยอดเศษสตางค์
- **ข้อเสนอแนะให้ Claude:** เพิ่มตัวเลือก "ปัดเศษเข้าบัญชีกำไร/ขาดทุนจากเศษสตางค์ (Rounding Difference Account)" ใน Service ชำระเงิน เพื่อสามารถตัดปิด Open Item ได้ทันทีเมื่อผลต่างไม่เกินเกณฑ์ที่กำหนด (เช่น ไม่เกิน 1.00 บาท)

#### 3. การตรวจสอบย้อนกลับของ Lot สินค้าแปรรูป (Traceability in `StockTransformService`)
- **ไฟล์ที่เกี่ยวข้อง:** `app/Services/Inventory/StockTransformService.php`, `app/Models/Lot.php`
- **เงื่อนไข/ปัญหา:** ในกระบวนการตัดแต่งเนื้อสัตว์ (Stock Transform / Production) มีการตัดสต็อกวัตถุดิบ (Parent Lot) และสร้างชิ้นส่วนใหม่ (Child Lot) แต่ปัจจุบันความสัมพันธ์ระหว่าง Parent Lot กับ Child Lot ถูกผูกแบบหลวมผ่านประวัติ Transaction
- **ข้อเสนอแนะให้ Claude:** เพิ่มฟิลด์ `parent_lot_id` ในตาราง Lot หรือสร้างตารางความสัมพันธ์ `lot_transform_lineage` เพื่อรองรับข้อกำหนด Food Safety / ISO 22000 ในการตรวจสอบย้อนกลับ (Traceability) เมื่อจำเป็นต้องเรียกคืนสินค้า (Recall)

#### 4. การตรวจสอบความสมบูรณ์ของการ Reversal บัญชี GL เมื่อเอกสารถูก Void
- **ไฟล์ที่เกี่ยวข้อง:** `app/Services/Accounting/GeneralLedgerService.php`, Service เอกสารการค้าทุกตัว
- **เงื่อนไข/ปัญหา:** เมื่อเอกสารการค้า (Credit Sale, Cash Sale, Purchase, Stock Adjustment) ถูก Void ต้องมั่นใจว่ามีการบันทึก Journal Voucher แบบ Reversal ยอดเดบิต/เครดิต หรือบันทึกสถานะ Voided ครบถ้วนทุกมิติ รวมถึงการคืนยอดการเคลื่อนไหวใน Stock Card
- **ข้อเสนอแนะให้ Claude:** พัฒนา Automated Integrity Test เพื่อสุ่มเอกสารที่มีการ Void แล้วตรวจเช็กความสมดุลของ Trial Balance และ Stock Balance ว่าไม่มียอดลอยหลงเหลืออยู่ในงบการเงิน

#### 5. การควบคุมลำดับเลขที่ใบกำกับภาษีเต็มรูป (Gapless Tax Invoice Sequence)
- **ไฟล์ที่เกี่ยวข้อง:** `app/Services/Sales/TaxInvoiceService.php`, `app/Services/Accounting/TaxComplianceService.php`
- **เงื่อนไข/ปัญหา:** ตามระเบียบกรมสรรพากร เลขที่ใบกำกับภาษีต้องเรียงลำดับต่อเนื่อง ห้ามมีเลขที่กระโดด (Gapless Sequence) หากมีการยกเลิกใบกำกับภาษี ต้องคงเลขที่นั้นไว้ในรายงานภาษีขายโดยแสดงสถานะ "ยกเลิก"
- **ข้อเสนอแนะให้ Claude:** ตรวจสอบระบบออกเลขที่ใบกำกับภาษีและการแสดงผลในรายงานภาษีขาย (ภ.พ.30) ให้เป็นไปตามระเบียบสรรพากรอย่างสมบูรณ์
