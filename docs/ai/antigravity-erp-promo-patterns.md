## 1. สรุปภาพรวมการดำเนินงาน

ตามข้อกำหนดใน `ANTIGRAVITY_TASK_ERP_PROMO_PATTERNS.md` ได้ดำเนินการปรับปรุงระบบโปรโมชันและแคมเปญซื้อครบ โดยยึดหลักการออกแบบตามระบบ BPlus ที่ร้านใช้งานจริง และรักษาความถูกต้องทางตัวเลขอย่างเคร่งครัด:

1. **การ์ดแม่แบบโปรโมชัน 7 รูปแบบ BPlus บนหน้าจอ `/qty-promotions`**:
   - ออกแบบการ์ดเลือกรูปแบบตามภาษาที่ผู้ใช้งานคุ้นเคยใน BPlus
   - ระบบตั้งค่า `promo_type` อัตโนมัติและแสดง/ซ่อนช่องกรอกที่เกี่ยวข้อง พร้อมข้อความแนะนำตัวอย่างการใช้งาน
2. **ปุ่ม "ใช้อีกครั้ง" (Copy Campaign)**:
   - เพิ่มปุ่มในทุกแถวของตารางรายการแคมเปญ
   - คัดลอกพารามิเตอร์ทั้งหมดเข้าสู่ฟอร์มสร้างใหม่โดยอัตโนมัติ โดยเว้นช่องรหัสไว้เพื่อให้ระบบสร้างรหัสใหม่ผ่าน `AutoCode` ไม่ให้ชนกับแคมเปญเดิม
   - บันทึกผ่าน route เดิม `POST /qty-promotions` (`QtyPromotionController::store`) โดยไม่สร้าง route บันทึกใหม่
3. **การแสดงวัน-เวลาและสถานะ 4 รูปแบบ**:
   - ปรับการระบุวันเวลาเป็น `datetime-local` ละเอียดระดับนาที
   - แสดงป้ายสถานะชัดเจน 4 รูปแบบ: `ยังไม่เริ่ม` (สีเหลืองเตือน), `กำลังใช้` (สีเขียวสำเร็จ), `หมดเวลา` (สีเทา), และ `ปิด` (สีขาวขอบเทา)
4. **ปรับป้ายชื่อเมนูใน `ErpMenu.php`**:
   - เปลี่ยนชื่อเมนู `/qty-promotions` เป็น **"โปรโมชัน / แคมเปญ"**
   - เปลี่ยนชื่อเมนูเดิม `/promotions` เป็น **"ส่วนลดราคาสินค้า (แบบเดิม)"** (แก้ไขเฉพาะป้ายชื่อ label เท่านั้น)
5. **ชุดทดสอบครอบคลุมทั้ง PHP และ Python**:
   - PHPUnit: `tests/Feature/QtyPromotionPatternsTest.php` ครอบคลุมการสร้าง 7 การ์ด, การตรวจจับ Error ภาษาไทย, ฟังก์ชันใช้อีกครั้ง, ขอบเขต POS query scope (-1 นาที, ระหว่าง, +1 นาที, ข้ามสาขา) และสถานะทั้ง 4 แบบ (ผ่าน 100%)
   - Python Pytest: `apps/pos-python/tests/test_promotion_patterns.py` ทดสอบการคำนวณส่วนลดถูกต้องระดับสตางค์, การตัดช่วงเวลา, ข้ามเที่ยงคืน และเขตเวลา Asia/Bangkok

## 2. ตารางแม่แบบโปรโมชัน 7 รูปแบบ (BPlus Patterns)

| # | การ์ดแม่แบบ BPlus | promo_type | ช่องข้อมูลที่เปิดให้กรอก | ตัวอย่างการใช้งานจริง |
|---|---|---|---|---|
| 1 | **ซื้อครบ X ชิ้น ราคาเหลือ Y บาท** | `bundle_price` | สินค้า (`product_id`), จำนวน X (`min_qty`), ราคาชุด Y (`bundle_price`) | 3 แพ็ค 100 บาท, 4 แพ็ค 100 บาท |
| 2 | **ซื้อ X แถม Y (1 แถม 1)** | `free_item` | สินค้า (`product_id`), ซื้อครบ X (`min_qty`), ของแถม (`free_product_id`), จำนวนแถม Y (`free_qty`) | ซื้อ 1 แถม 1, ซื้อ 2 แถม 1 |
| 3 | **ซื้อครบ X ชิ้น ลด % / บาท** | `discount` | สินค้า (`product_id`), จำนวน X (`min_qty`), ประเภทส่วนลด (`discount_type`), มูลค่า (`discount_value`) | ซื้อครบ 2 ชิ้น ลด 10 บาท หรือ ลด 10% |
| 4 | **เลือกซื้อคละครบ X ชิ้น (ราคาเหลือ/ลด)** | `mix_bundle` | กลุ่มสินค้า (`product_ids[]`), จำนวน X (`min_qty`), ราคาชุด Y (`bundle_price`) | คละรส 3 ถุง 100 บาท |
| 5 | **ซื้อครบยอด X บาท ลด** | `bill_discount` | ยอดซื้อขั้นต่ำ X (`min_amount`), ประเภทส่วนลด, มูลค่า (`discount_value`), ลดสูงสุด (`max_discount`) | ยอดบิลครบ 1,000 บาท ลด 50 บาท |
| 6 | **ซื้อครบยอด X บาท ได้ของแถม** | `bill_free_item` | ยอดซื้อขั้นต่ำ X (`min_amount`), ของแถม (`free_product_id`), จำนวนแถม (`free_qty`) | ยอดบิลครบ 500 บาท แถมน้ำ 1 ขวด |
| 7 | **ซื้อครบยอด X บาท แลกซื้อ** | `bill_addon` | ยอดซื้อขั้นต่ำ X (`min_amount`), สินค้าแลกซื้อ (`product_id`), ราคาแลกซื้อ (`bundle_price`), สิทธิ์ต่อบิล (`free_qty`) | ยอดบิลครบ 300 บาท แลกซื้อน้ำมัน 19 บาท |

## 3. รายละเอียดการส่งต่อ Claude: เรื่องสูตรโปร/ส่วนลด

ตามเงื่อนไขข้อ 40: *"ถ้าเทสต์ตัวคิดเงินไม่ผ่าน (สูตรผิด): ห้ามแก้ `promotions.py` หรือ service คิดเงินเอง — ทำเครื่องหมาย `skip` พร้อมเหตุผล และเขียนลงรายงาน "ส่งต่อ Claude" พร้อมตัวเลขที่คาดหวังกับที่ได้"*

ทีมงานได้ตรวจสอบและสรุปประเด็นด้านสูตรการคำนวณใน `apps/pos-python/pos_python/promotions.py` ไว้ดังนี้:

### ประเด็นที่ 1: โปรโมชันระดับบิล (`bill_discount`, `bill_free_item`, `bill_addon`) บน POS Python
- **พฤติกรรมปัจจุบัน**: ฟังก์ชัน `promotion_discounts(lines, promotions)` ใน `promotions.py` ออกแบบมาสำหรับ line-level promotion โดยเริ่มวนหา `trigger_index = first(promotion.product_id)` หากโปรโมชันไม่มี `product_id` (เช่น โปรระดับท้ายบิล `bill_discount` ซึ่งอิงตามยอดรวมทั้งบิล) ระบบจะข้ามไป ทำให้ไม่เกิดส่วนลด
- **ตัวเลขทดสอบ**:
  - ยอดซื้อรวมทั้งบิล: 500.00 บาท (สินค้า 5 ชิ้น ชิ้นละ 100 บาท)
  - โปรโมชัน: ยอดครบ 500 ลด 10% (`bill_discount`)
  - **ตัวเลขที่คาดหวัง**: ลด 50.00 บาท (ยอดสุทธิ 450.00 บาท)
  - **ตัวเลขที่ได้จริงใน Python POS**: ลด 0.00 บาท (ไม่มีการลด)
- **การจัดการ**: ทำเครื่องหมาย `@pytest.mark.skip` ใน `test_bill_discount_over_threshold` พร้อมระบุเหตุผลว่า POS ปัจจุบันยังคำนวณเฉพาะโปรต่อรายการ (สอดคล้องกับคอมเมนต์ใน `PosController.php` ที่ระบุว่า POS รุ่นก่อนหน้ายังไม่รองรับโปรต่อบิล)

### ประเด็นที่ 2: โปรโมชัน "1 แถม 1" สินค้าตัวเดียวกัน เมื่อตั้งค่า `min_qty=1, free_qty=1`
- **พฤติกรรมปัจจุบัน**: ใน `promotions.py` บรรทัดที่ 58-79 หาก `product_id == free_product_id` (สินค้าที่ซื้อกับของแถมเป็นตัวเดียวกัน) ตัวแปร `trigger` และ `gift` จะชี้ไปยังบรรทัดเดียวกันในตะกร้า (`trigger_index == gift_index`):
  ```python
  sets = (trigger.qty / promotion.min_qty).to_integral_value(rounding=ROUND_FLOOR)
  amount = min(gift.qty, sets * promotion.free_qty) * _price(gift)
  ```
  หากกำหนด `min_qty=1, free_qty=1` และลูกค้าหยิบสินค้า 3 ชิ้น (ชิ้นละ 50 บาท):
  - `sets = 3 / 1 = 3 ชุด`
  - `amount = min(3, 3 * 1) * 50 = 150.00 บาท` (คิดฟรีทั้ง 3 ชิ้น แทนที่จะฟรี 1 ชิ้น)
- **ตัวเลขทดสอบ**:
  - ลูกค้าซื้อ 3 ชิ้น ชิ้นละ 50 บาท (ยอดตั้งต้น 150.00 บาท)
  - โปรโมชัน 1 แถม 1 (คาดหวังซื้อ 2 ได้ 1 ชุดฟรี 1 ชิ้น ชิ้นที่ 3 จ่ายปกติ)
  - **ตัวเลขที่คาดหวัง**: ลด 50.00 บาท (จ่าย 100.00 บาท)
  - **ตัวเลขที่ได้จริงเมื่อตั้ง min_qty=1**: ลด 150.00 บาท (จ่าย 0.00 บาท)
- **แนวทางและข้อสังเกต**:
  - หากตั้งค่าแบบคู่ซื้อ (`min_qty=2, free_qty=1`) ในระบบ Python จะคำนวณได้ถูกต้องเป๊ะ ลด 50.00 บาท (ทดสอบผ่านใน `test_free_item_paired_trigger_and_gift`)
  - หากต้องการให้ `min_qty=1` แยกสินค้าที่จ่ายเงินออกจากสินค้าของแถมเมื่อเป็น SKU เดียวกัน จำเป็นต้องปรับอัลกอริทึมใน `promotions.py` ให้หักลบจำนวนชุดที่ถูกใช้เป็น trigger ออกก่อนคำนวณ gift
  - ได้ทำเครื่องหมาย `@pytest.mark.skip` ใน `test_free_item_identical_product_min_qty_one` เพื่อส่งต่อให้ Claude ดำเนินการปรับปรุงสูตรต่อไป

### ประเด็นที่ 3: การตรวจจับช่วงเวลาแบบนาที (Hour/Minute Precision) ใน POS Python
- **พฤติกรรมปัจจุบัน**: ฟังก์ชัน `active_promotions()` ใน `promotions.py` ตรวจสอบเฉพาะวันที่ (`starts_date` และ `ends_date` รูปแบบ `YYYY-MM-DD`):
  ```python
  WHERE (starts_date IS NULL OR substr(starts_date, 1, 10) <= ?)
    AND (ends_date IS NULL OR substr(ends_date, 1, 10) >= ?)
  ```
  ดังนั้น การเริ่ม/สิ้นสุดโปรโมชันระดับนาที (เช่น เริ่ม 10:00 จบ 14:00) ในเครื่อง POS ออฟไลน์ จะยังอิงตามวันจนกว่าจะมีการ sync ข้อมูลรอบใหม่จากเซิร์ฟเวอร์
- **การจัดการ**: ทำเครื่องหมาย `@pytest.mark.skip` ใน `test_minute_level_time_window_in_pos_python` และส่งต่อให้ Claude พิจารณาเพิ่มคอลัมน์ `starts_at`/`ends_at` ในตาราง SQLite ของ POS ต่อไป
