# Report Catalog — รายงานชุดแรกของ POPSTAR ERP

วันที่: 2026-08-22 · ผู้ทำ: Claude · อ้างอิง: `CLAUDE_LEGACY_REBUILD_BRIEF.md` หัวข้อ "งานระยะที่ 2A"

เอกสารนี้คือ catalog ของรายงาน **20 ตัวในชุดแรก** ที่ต้องทำก่อน ไม่ใช่ทะเบียนรายงานเดิม
1,502 ตัว (อันนั้นอยู่ที่ `docs/ai/legacy-report-catalog.md` + `docs/ai/legacy/reportfile-index.csv`)

ทะเบียนที่ระบบใช้จริงอยู่ในตาราง `report_definitions` — เอกสารนี้เป็นคำอธิบายประกอบ
ที่บอก "ทำไม" และ "ยังขาดอะไร" ซึ่งใส่ลงตารางไม่หมด

## สถานะที่ใช้ในเอกสารนี้

| สถานะ | ความหมาย |
|---|---|
| `พร้อม` | มีหน้าจอ มีข้อมูล ทำ UAT ได้ทันทีเมื่อได้ตัวอย่างยอดจริง |
| `ขาดข้อมูล` | มีหน้าจอหรือเขียนได้ แต่ตารางในระบบใหม่ยังว่าง จึงยัง UAT ไม่ได้ |
| `ขาดโครงสร้าง` | ทำไม่ได้เลยจนกว่าจะเพิ่มคอลัมน์/ตาราง — ต้องแก้ schema ก่อน |
| `ยังไม่มี` | ต้องเขียนใหม่ทั้งหมด แต่ข้อมูลต้นทางมีแล้ว |

> **ช่อง "ความถี่" และ "เจ้าของ" ยกมาจาก brief ทั้งหมด ยังไม่มีใครยืนยัน**
> ต้องให้เจ้าของ/หัวหน้าฝ่ายยืนยันว่าใช้ทุกวันจริงไหมและใครเป็นเจ้าของรายงาน
> ก่อนจะถือว่า catalog ปิดได้ — นี่เป็นช่องเดียวในเอกสารที่ผมเดาไม่ได้

## P0 — ตามลำดับที่เจ้าของสั่ง

### 1. ใบจองคงค้างและสถานะส่งสินค้า (`booking.outstanding`)

- **ความถี่ / เจ้าของ**: ทุกวัน · ฝ่ายขาย + คลัง · ต้นแบบเดิม `POPSTAR2022` "รวมใบจอง"
- **ใช้ตัดสินใจ**: ของที่ลูกค้าจองไว้ยังไม่ได้ส่ง มีอะไรบ้าง ต้องเตรียมของวันไหน และใบไหนค้างนานผิดปกติ
- **ข้อมูล/สูตร**: `sale_bookings` (status, confirmed_document_id) JOIN `documents` (doc_date, customer, branch)
  JOIN `document_items`; คงค้าง = `status = 'pending'` และยังไม่มี `confirmed_document_id`;
  อายุใบจอง = วันนี้ − `doc_date`
- **สถานะ**: **`ขาดข้อมูล`** — โครงสร้างพอทำได้ แต่ `sale_bookings` บน production มี **0 แถว**
  และ ERP ใหม่มีรายงาน `pending_bookings` อยู่แล้ว จึงควรต่อยอดตัวเดิมแทนที่จะเขียนใหม่

### 2. ใบจองครบกำหนด/เกินกำหนดส่ง (`booking.due`)

- **ความถี่ / เจ้าของ**: ทุกวัน · ฝ่ายขาย + ผู้จัดการ
- **ใช้ตัดสินใจ**: ใบไหนเลยกำหนดส่งแล้ว ต้องเร่ง/แจ้งลูกค้า/ยกเลิก
- **ข้อมูล/สูตร**: ต้องมี **วันครบกำหนดส่ง** ต่อใบจอง แล้ว `เกินกำหนด = due_date < วันนี้ AND ยังไม่ confirmed`
- **สถานะ**: **`ขาดโครงสร้าง`** ⚠️ — `sale_bookings` มีแค่
  `document_id, salesman_id, sales_area_id, status, confirmed_at, confirmed_document_id`
  **ไม่มีฟิลด์วันครบกำหนดส่งเลย** และ `documents` ก็ไม่มี `due_date` (มีเฉพาะใน `customer_open_items`
  ซึ่งเป็นวันครบกำหนด*ชำระเงิน* คนละความหมาย)

  **ต้องทำก่อน**: migration เพิ่ม `delivery_due_date` (และสถานะส่งของ ถ้าจะแยกส่งบางส่วน)
  พร้อมช่องกรอกในหน้าใบจอง — ไม่มีอันนี้รายงานเกิดไม่ได้ ไม่ว่าจะเขียน query เก่งแค่ไหน

### 3. ใบจองตามสาขา/สายขาย/พนักงานขาย (`booking.by_branch_seller`)

- **ความถี่ / เจ้าของ**: ทุกวัน · ผู้จัดการขาย
- **ใช้ตัดสินใจ**: สายขายไหน/เซลล์คนไหนมียอดจองค้างเท่าไร ใช้กระตุ้นการปิดการขาย
- **ข้อมูล/สูตร**: group `sale_bookings` ตาม `documents.branch_id`, `sale_bookings.sales_area_id`,
  `sale_bookings.salesman_id` — ทั้งสามฟิลด์มีครบแล้ว
- **สถานะ**: **`ขาดข้อมูล`** — โครงสร้างพร้อม รอข้อมูลจริง (มี `BookingSalesAreaTest` 4 เคสคุมอยู่แล้ว)

### 4. รายละเอียดยอดเจ้าหนี้คงค้าง (`ap.outstanding_detail`) และ 5. อายุหนี้เจ้าหนี้ (`ap.aging`)

- **ความถี่ / เจ้าของ**: ทุกวัน · บัญชี + จัดซื้อ · ต้นแบบเดิม `SQLAP569005`
- **ใช้ตัดสินใจ**: ต้องจ่ายใครก่อน วางแผนเงินสดออก และเช็คว่าเจ้าหนี้รายไหนเกินกำหนด
- **ข้อมูล/สูตร**: ยอดคงค้าง = ใบซื้อเชื่อ (`documents` type `PURCHASE`) − ใบสำคัญจ่าย/การจ่ายที่ตัดแล้ว;
  aging bucket ตามวันครบกำหนดชำระ (ปกติ 0-30 / 31-60 / 61-90 / 90+)
- **สถานะ**: **`ขาดโครงสร้าง`** ⚠️ — ฝั่งลูกหนี้มี `customer_open_items` ที่มี `due_date`,
  `paid_amount`, `balance_amount`, `status` ครบ **แต่ฝั่งเจ้าหนี้ไม่มีตารางคู่ขนาน**
  `supplier_ledger` มีแค่ `entry_type/amount/balance_after/entry_date` ซึ่งเป็นสมุดเดินบัญชี
  ไม่ใช่ open item จึงทำ aging ต่อใบไม่ได้ และตอนนี้มี 0 แถว

  **ต้องทำก่อน**: ตาราง `supplier_open_items` แบบเดียวกับฝั่งลูกหนี้ + เขียนค่าตอนตั้งหนี้/จ่ายเงิน

### 6. สมุดเงินสดรายวัน (`cash.daily_cash_book`)

- **ความถี่ / เจ้าของ**: ทุกวัน · การเงิน · ต้นแบบเดิม `CAS0103002`
- **ใช้ตัดสินใจ**: เงินสดในมือวันนี้ควรมีเท่าไร ตรงกับที่นับจริงไหม
- **ข้อมูล/สูตร**: ยอดยกมา + รับ − จ่าย = คงเหลือ แยกตามสาขาและวัน
- **สถานะ**: **`ขาดข้อมูล`** — ตาราง `cash_books` มีครบ (`branch_id, entry_date, debit, credit, balance`)
  แต่มี **0 แถว** และมีที่เขียนเข้าอยู่ที่เดียวคือ `BplusOperationController::storeCashBook`
  ซึ่งเป็นหน้ากรอกมือ **ยังไม่มีเอกสารใดของระบบเดินรายการเข้าสมุดเงินสดอัตโนมัติ**
  ถ้าปล่อยแบบนี้ สมุดเงินสดจะไม่มีวันตรงกับยอดขาย/รับชำระ

### 7. สรุปยอดธนาคารตามบัญชี (`cash.bank_summary`) และ 8. กระทบยอด statement (`cash.bank_reconciliation`)

- **ความถี่ / เจ้าของ**: ทุกวัน · การเงิน + บัญชี · ต้นแบบเดิม `BK01030001`
- **ใช้ตัดสินใจ**: เงินเข้าบัญชีตรงกับที่ระบบบันทึกไหม รายการไหนยังไม่ถูกจับคู่
- **ข้อมูล/สูตร**: `bank_accounts` × `bank_statements` เทียบกับ `payment_documents`/`pos_payments`;
  รายการที่จับคู่ไม่ได้ = ยอดรอพิสูจน์
- **สถานะ**: **`ขาดข้อมูล`** — มีทั้ง model, route และ `BankReconciliation` แล้ว
  แต่ `bank_accounts`, `bank_statements`, `bank_reconciliations` เป็น **0 แถวทั้งหมด**
  ต้องเปิดบัญชีธนาคารในระบบและนำเข้า statement จริงก่อนถึงจะ UAT ได้

### 9. ยอดขายรายวัน แยก POS / ขายสดหลังบ้าน / ขายเชื่อ (`sales.daily_by_channel`)

- **ความถี่ / เจ้าของ**: ทุกวัน · ผู้จัดการ + การเงิน
- **ใช้ตัดสินใจ**: ยอดขายวันนี้แต่ละช่องทางเท่าไร ใช้กระทบยอดกับเงินสด/ธนาคารตอนปิดวัน
- **ข้อมูล/สูตร**: `sales_postings` มี `channel` (`POS` / `CASH_SALE` / `CREDIT_SALE`) อยู่แล้ว —
  group by `sale_date`, `channel`, `branch_id` แล้ว sum `net_sales`
- **สถานะ**: **`ยังไม่มี`** แต่ทำง่ายที่สุดในชุดนี้ — รายงาน `daily_sales` ปัจจุบันอ่าน `sales_postings`
  อยู่แล้วแต่ไม่ได้แยก channel
  ⚠️ **ติดบล็อกที่ P0-1 ของ readiness audit**: ตอนนี้ `sales_postings` มีบิล POS เก่าที่นำเข้ามา
  16,537 ใบปนอยู่ ยอดจะผิดจนกว่าจะจัดการข้อมูลชุดนั้น

### 10. การรับชำระและยอดเงินรอพิสูจน์ (`payment.received_and_unidentified`)

- **ความถี่ / เจ้าของ**: ทุกวัน · การเงิน
- **ใช้ตัดสินใจ**: เงินเข้าวันนี้เท่าไร ตัดหนี้ใครไปแล้วบ้าง และมีเงินก้อนไหนที่ยังไม่รู้ว่าของใคร
- **ข้อมูล/สูตร**: รับชำระ = `payment_documents` + `payment_allocations`;
  รอพิสูจน์ = ยอดรับที่ยังไม่ถูก allocate + `pos_payments` วิธี QR ที่จับคู่ statement ไม่ได้
- **สถานะ**: **`ขาดข้อมูล`** — `payment_documents`, `payment_allocations`, `payment_lines` เป็น 0 แถว
  ส่วน `pos_payments` มี 25,447 แถว (ส่วนใหญ่มาจากบิล POS เก่าที่นำเข้า)
  หน้า `pos/control` แสดง QR ที่ยังไม่จับคู่อยู่แล้ว ใช้เป็นจุดตั้งต้นได้

## สรุปสิ่งที่ต้องแก้ schema ก่อน (ไม่ใช่แค่เขียน query)

รายงาน P0 สองกลุ่มนี้ทำไม่ได้เลยจนกว่าจะเพิ่มโครงสร้าง — ควรตัดสินใจก่อนลงมือทำหน้าจอ

1. **วันครบกำหนดส่งของใบจอง** — `sale_bookings` ไม่มีฟิลด์นี้ ทำให้ P0 ข้อ 2 เกิดไม่ได้
2. **open item ฝั่งเจ้าหนี้** — ไม่มีตารางคู่ขนานกับ `customer_open_items` ทำให้ AP aging เกิดไม่ได้
3. **ตัวเดินรายการเข้าสมุดเงินสด** — `cash_books` ไม่มีอะไรเขียนเข้าอัตโนมัติ สมุดเงินสดจึงไม่มีวันตรงยอด

## สิ่งที่ต้องได้จากเจ้าของก่อนปิด catalog

1. ยืนยัน **ความถี่จริง** และ **ชื่อเจ้าของรายงาน** ของทั้ง 20 ตัว (ตอนนี้ยกมาจาก brief ล้วน)
2. ตัวอย่างผลลัพธ์จริง 1 ชุดต่อรายงาน พร้อมช่วงวันที่และสาขาที่ใช้ดึง เพื่อทำ UAT
3. ตัดสินใจเรื่องข้อมูล POS เก่า 16,537 ใบ (P0-1 ใน `erp-readiness-audit.md`) เพราะรายงานยอดขาย
   ทุกตัวจะผิดจนกว่าจะจัดการเรื่องนี้ และตอนนี้ยังเจอตาราง staging ของการนำเข้าเดิมค้างอยู่ด้วย
   (`imported_payments` 37,412 แถว, `imported_receipts`, `import_batches` — ไม่มีโค้ดอ้างถึงแล้ว)
