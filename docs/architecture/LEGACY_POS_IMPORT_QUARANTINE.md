# Legacy POS Import — Quarantine

วันที่ตัดสินใจ: 2026-08-23 · ผู้ตัดสินใจ: เจ้าของโครงการ · สถานะ: **กักบริเวณ ยังไม่ลบ**

## เรื่องคืออะไร

ก่อนหน้านี้มีท่อนำเข้าประวัติ POS จากระบบเก่า ท่อถูกลบไปแล้วใน `d24c99d`
(เหลือโฟลเดอร์ว่าง `app/Services/PosImport/`) แต่ **ข้อมูลที่นำเข้าไปแล้วยังอยู่บน production**

| ตาราง | จำนวนแถว (ตรวจ 2026-08-22) |
|---|---|
| `pos_receipts` ที่ไม่มี `document_id`/`pos_shift_id` | 16,537 จาก 16,557 |
| `imported_payments` | 37,412 |
| `imported_receipts`, `imported_receipt_items`, `import_batches`, `import_files`, `import_errors` | staging ที่เหลือ |

ผลกระทบ: `sales_postings` รายงาน 4,599,908.50 บาท ขณะที่ `gl_journals` มี 23,479.77 บาท
ต่างกัน ~4.58 ล้าน และ 16,537 แถวไม่มีต้นทุน รายงานกำไรทุกตัวจึงไม่มีความหมาย

## กติกาที่ใช้ตอนนี้

1. **ห้ามลบข้อมูล** จนกว่าจะมี backup และกำหนด retention/audit ที่ชัดเจน
2. **ห้ามมี route, job, command หรือโค้ดใหม่** อ่านหรือเขียนตาราง staging เหล่านี้
   บังคับด้วยเทสต์ `tests/Feature/LegacyPosImportQuarantineTest.php` ซึ่งจะแดงทันทีถ้ามีใครอ้างถึง
3. **ห้าม import ประวัติ POS เก่ากลับเข้าระบบใหม่** ไม่ว่าเหตุผลใด
4. migration ที่สร้างตารางเหล่านี้ยังอยู่ตามเดิม (ประวัติการสร้างตารางย้อนหลังไม่ได้)
   เทสต์จึงไม่ตรวจโฟลเดอร์ `database/migrations`

## ข้อควรรู้เมื่อทำรายงาน

รายงานยอดขายทุกตัวที่อ่าน `sales_postings` **ยังนับ 16,537 บิลเก่าอยู่**
ตราบใดที่ยังไม่จัดการเรื่องนี้ ตัวเลขรายงานจะไม่ตรงกับบัญชี — ห้ามใช้ทำ UAT เทียบยอด
จนกว่าจะแยกข้อมูลชุดเก่าออกได้

## ทางเลือกที่เสนอไว้ (ยังไม่ตัดสิน)

1. ย้ายไป schema `legacy_*` แยก แบบอ่านอย่างเดียว
2. เติมคอลัมน์ flag แล้วกันออกจาก view `sales_postings`
3. ลบทิ้งหลัง backup + อนุมัติ retention

ทุกทางต้องมีรายงานกระทบยอดก่อน/หลัง และต้อง backup ก่อนเสมอ
